# #886 再審査: 端末ログイン保持と運用者回復を現行認証へ統合

2026-09-08。旧 #886 は端末資格情報の基盤だけを持ち、全端末失効時の epoch を JWT/WS 側で確認していなかった。ブラウザ保存・端末管理・運用者回復にも配線がなかった。本変更は仕様と実装の両方を更新する。

## 設計

正本は [端末セッション・運用者回復](passkey-default-authentication.md)。旧 PR 本文の「パスキー既定」や三モード分離を、この再審査の受け入れ条件にしない。Google OIDC、MFA、パスワード、公開パスキー登録を残し、ブラウザが明示的に希望した端末ログイン保持を追加する。

現在の local main 9b7b796 を基点とする。#1545 の企業 SSO は別 PR であり、このブランチには未取り込み。共通の認証事実の契約を揃えるが、企業ポリシーの確認を端末 Cookie に置き換えない。

## 実装内容

- パスキー確認後だけ HttpOnly Cookie を発行し、access JWT はメモリ保持。30日の絶対期限と元の認証時刻を更新で延長しない。単一タブと複数タブで更新を調整し、応答消失時は同じ rotation ID を再利用する。
- 現ユーザー・端末・パスキー・鍵世代の失効を JWT、refresh、auth-code、OIDC、WS の確認へつなぐ。接続中 WS の操作・通知も確認し、旧形式の再開セッションは拒否する。
- 端末管理 UI と運用者回復 UI、回復リンク受領画面を追加。管理変更は接続済み WS と fresh action proof が必要。回復時は新規パスキー登録、旧資格情報失効、grant 消費を1トランザクションにする。
- 認証リンクの開始時と完了時も発行元の失効を確認する。Cr ブラウザの user WS は既存の bearer subprotocol を使用し、URL へ JWT を載せない。
- migration を050–053に整理。旧 Device 行を認証済み扱いにせず、初期状態は CERNERE_DEVICE_SESSIONS_ENABLED=false とする。

## 受け入れ条件

- 古い token、失効済み端末、回復前の session/grant、発行者権限変更後の grant を再利用できない。
- 同時回復が二重成功せず、キー挿入等の失敗では全変更が rollback する。
- 現在端末の失効で画面がログアウトし、別端末の失効で有効なパスキーを失わない。
- 対応ブラウザでパスキー・Cookie 復帰・複数タブ・通信断からの再試行を確認する。
- Google/MFA を維持し、#1545 と併合する際は企業認可とこの PR の失効確認の両方を保持する。

## 有効化時の作業

承認・マージ後、migration 履歴、HTTPS/RP origin、session master key と key ID の登録を確認して機能を有効化する。設定登録やサービス再起動はこの変更で実施していない。外部サービスの発行済み Cookie/token の即時失効は保証対象外。
