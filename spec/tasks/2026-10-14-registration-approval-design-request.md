# 依頼: ユーザー登録の許可制の設計案 (Astra)

## 人間 (neco) の指示の原文

> 攻撃耐性を検証
> Crはサービス共通にんしょうでもあり他人の公開データにアクセスする権限もある。
> ユーザーの登録を許可制(後からロックアウト可、許可されるまでは他人は読めず自分しか使えない最低限の権限)にする案も用意したい。

## 前提

- Cernere (Cr) はパスキーのみの認証へ移行中。誰でも「パスキーで続ける」から即時にアカウントを作れる。
  設計: `E:/Document/Ars/Cernere/.wt-passkey-only/spec/plan/2026-10-14-passkey-only-authentication.md`
- 実装はブランチ `feat/passkey-only-auth` (`E:/Document/Ars/Cernere/.wt-passkey-only`)。コードはここを読む。
- Cr は本運用前で、切替時に DB をリセットする。既存ユーザーの移行は考えなくてよい。

## 設計してほしいこと

独立に考えてよい。

1. **他人のデータに届く経路の洗い出し**: Cr の中 (WS コマンド `server/src/commands.ts`、relay、組織・メンバー、project/service 向けの user data・data sharing・identity roster、export、OIDC userinfo など) と、Cr を信用する他サービスへの経路 (composite の authCode/exchange、user×project token、OIDC クライアント、project_data 行の自動作成など)。ファイル・関数つきの表にする。
2. **状態モデル**: 例 `pending` (許可待ち) / `active` / `locked` (ロックアウト)。誰が許可・ロックするか (admin、組織 admin、招待)、許可の単位 (Cr 全体 / サービスごと)、ロックアウト時に失効させるもの (セッション、端末、WS、発行済みトークン、他サービス側)。
3. **許可待ちの最低限の権限**: 「自分しか使えない」範囲を具体的に (自分のプロフィール・パスキー・リカバリー QR・通知先・アカウント削除はできる、他人の検索・閲覧・relay・組織参加・サービスへのログインはできない、など)。各経路 (1 の表) をどう塞ぐか。
4. **他サービスへの伝え方**: 許可待ちのユーザーに authCode / exchange / project token / OIDC を出すか。出すならトークンのクレームでどう伝え、サービスにどう強制するか。出さないならサービスの画面でどう案内するか。
5. **許可の運用**: 許可申請の通知 (管理者への知らせ方)、許可・拒否・ロックの UI と監査、招待コードによる事前許可の要否、許可待ちアカウントの放置・自動削除。
6. **攻撃耐性**: 許可制で防げるもの・防げないもの、許可待ちアカウントの大量作成 (リソース消費・管理者への通知洪水)、管理者へのソーシャルエンジニアリング。
7. **案の比較**: 少なくとも「A: 全体許可制」「B: サービスごとの許可 (Cr 自体は即時、他人データとサービスログインは許可制)」を比べ、推奨を 1 つ選ぶ。
